# Deployment Topology Model

RTNN separates template capability, business release decisions, and deployment execution.

## Repository Roles

| Role | Responsibility |
| --- | --- |
| Template repository | Defines reusable backend/admin/app/weapp/client capabilities, contracts, and operational models. |
| Business repository | Owns business code, environment choices, release decisions, and non-sensitive project facts. |
| Deploy executor repository | Executes deploy, rollback, smoke checks, runtime env injection, facts collection, and static package distribution. |

The deploy executor does not decide what should be released. The business repository sends an explicit release instruction, and the deploy executor validates and executes it.

## Environment Model

RTNN recommends two long-lived remote environments:

- `testing`: receives validated integration builds and is allowed to cancel older in-flight deploys.
- `production`: receives explicitly promoted releases and should not cancel active deploys automatically.

Each environment should have:

- its own runtime env;
- its own compose project or platform namespace;
- its own public URLs;
- its own health/smoke targets;
- its own release facts.

## Runtime Facts

Runtime facts are generated by the deploy executor and may include:

- active version;
- source SHA;
- image tags;
- public URLs;
- health and smoke status;
- client release facts.

Runtime facts must not include secrets. Business repository `liveState` should be checked against runtime facts or written back from runtime facts, not maintained by hand in parallel documents.
